На насыщенном наборе из 50 000 позиций сохранение небольшой правки занимает около 12 секунд без HTTP и браузера. Независимые изменения разных пользователей конфликтуют на уровне всей базы. ## Фактическая карта системы

- Проектная база → позиции заявок → фактические поступления со ссылками на АПП/М-15 → редакции ЗНИ → АВК → выдача или фактический возврат заказчику.
- Рабочее хранилище — `.materials-workspace/workspace.json`. Главная страница ждёт его загрузки. `localStorage` служит копией для восстановления; серверная ревизия защищает от записи устаревшей вкладкой. Изменение одного документа отправляет весь workspace.
- Приёмка и остатки вычисляются из действующих подписанных документов, выдач и возвратов. АПП и М-15 одного поступления не являются двумя поступлениями. Возврат непринятого и возврат излишка по-разному влияют на остаток заявки.
- Загруженные оригиналы хранятся отдельно в `document-files`; файл реестра имеет собственную ревизию и очередь. PDF/Excel генерируются по запросу, общие документы в архиве не дублируются.
- Схема Drizzle есть, но действующий UI и его серверные функции не сохраняют этот маршрут в PostgreSQL. SQL-планы и индексы не объясняют текущие задержки. Тестовая PostgreSQL не настроена.

## Масштаб: реальные измерения

Синтетический набор на каждую позицию содержит отдельную заявку, поступление 10, подписанные ЗНИ и АВК с приёмкой 8, выдачу 1 и возврат непринятого 2. Ожидаемые остаток склада и доступность выдачи — 7. Материалы имеют разные наименования. Это насыщенная история, а не только 50 000 строк справочника и не прогноз точного размера пользовательской базы.

Замеры выполнены последовательно в Node, с сохранением только во временные каталоги. Полный набор тестов и сборка в момент измерения не запускались. ## Оставшиеся ограничения и порядок работ

1. **P1 — полная пересылка и перезапись workspace.** Даже изменение справочника повторно копирует, сериализует, проверяет и записывает всю историю. Для 50 000 насыщенных позиций задержка уже измеряется секундами. Приоритет: отдельные серверные операции над документами/позициями, транзакционное хранилище, индексы по связям и чтение нужных страниц. Сохранность подписанной истории и проверки остатков должны остаться серверными. Миграция требует отдельного разрешения.
2. **P1 — общая ревизия для всех пользователей.** Изолированный тест десяти клиентов, меняющих разные позиции одной исходной версии, получает **1 saved и 9 conflict**. Потеря обновлений предотвращается, но автоматического слияния независимых изменений нет. Для целевой команды нужны версии отдельных сущностей и разрешение конфликтов конкретного документа. Это проверка протокола в одном процессе, не нагрузка десяти браузеров.
3. **P1 при нескольких серверных процессах — нет общей блокировки файла.** Очереди workspace и оригиналов существуют внутри процесса. Несколько экземпляров с общей папкой не защищены общей транзакцией. Вывод статический; межпроцессная гонка в этой сессии не моделировалась. Масштабировать текущий файловый сервер несколькими процессами нельзя считать безопасным.
4. **P2 — загрузка и работа браузера.** Главная страница получает весь workspace, реестр документов — весь каталог. XLSX разбирается синхронно, поиск и построение представлений остаются на клиенте. Пагинация ограничивает DOM, но не эти вычисления. Нужны серверные страницы/поиск и отдельный worker для больших Excel-файлов. Живой UI с насыщенными 50 000 позициями и на слабом компьютере не измерен.
5. **P2 — браузерная копия.** Ошибка квоты `localStorage` не мешает серверному сохранению, что проверено тестами, но большая база может остаться без офлайн-копии. Следующий этап — хранение незавершённых изменений отдельно от полного snapshot, с явным состоянием локального восстановления.
6. **P2 — надёжность тестового прогона.** В обычном параллельном `pnpm test` три UI-сценария упали на ожидании фильтра/тайм-ауте печатного редактора. Эти же 24 теста прошли отдельно при одном worker, затем весь набор прошёл с `--maxWorkers=2`. Причина полностью не локализована; успешный повтор не доказывает отсутствие нестабильности. Ожидания тестов и ограничения ресурсов требуют отдельного внимания, бизнес-ожидания ради зелёного результата не изменялись.
7. **P3 — размер загрузки.** Production build предупреждает о чанках более 500 кБ: основной routes около 1,96 МБ (544 кБ gzip), Excel около 1,28 МБ (374 кБ gzip), PDF worker около 1,24 МБ. Это размеры артефактов, не измерение времени открытия. Разделение тяжёлых экранов и загрузка библиотек по действию остаются полезной отдельной работой.
8. **P3 — разрыв подписей длинной заявки.** Реальная печать заявки на 65 строк снова дала пять страниц: блок подписей разделён между четвёртой и пятой, на пятой повторяется шапка таблицы без материалов. Подтверждено визуально, количества и последняя строка присутствуют. Это оставшийся дефект из аудита 05.11; алгоритм разбиения пользовательских Excel-бланков в этой сессии не менялся.
